Test Evidence

"We tested it" is a claim. This document is the evidence: what was tested, in four layers, against the real database and the real deployed app — what it proved, and the three genuine defects it found on the way. All three are fixed, and the tests that found them now stand guard.

205 automated unit tests 20 live-database tests 10 browser steps on the deployed app 3 findings, all fixed Date: 24 October 2026

01 Why evidence, not a tick

The pipeline was already green when this pass began — 202 tests, clean build. The purpose of testing was not to turn the pipeline green. It was to find what the pipeline could not see.

A unit test proves a function behaves in the world the test constructs. It cannot prove the world matches. The only way to know whether the three-signature chain actually holds in production — where the database, the rules, the network and five real accounts all meet — is to walk it there, as real users, and to try to break it on purpose.

🎯
The measure of a test pass is what it found

This one found two security holes no existing test could see, and one place where a user gets stuck. If a test suite finds nothing, it usually is not looking hard enough — the findings below are the point, not an embarrassment.

Each layer proves a different kind of thing. Together they cover the logic, the contracts, the database and the screens.

🔒
Why layers 3 and 4 never run in CI

The live suite lodges real leave requests and signs real approvals in the production database. It is excluded from every automatic run — a deliberate split, so no push can ever write test data into production by accident. It runs only when someone types the command on purpose.

04 What the testing found

Three defects, none visible to the existing suite. All fixed the day they were found, all now pinned by a test.

🔓
Finding 1 — the self-approval hole (security)

A live test wrote status: approved straight to a pending request — as the employee who owned it — and the database allowed it. The three signatures could be forged with one write from a determined employee's console. The rules were tightened the same hour: the owner may now move status only to cancelled, and the identity, dates and day-counts on their request may never move at all. Re-tested against production: denied. The rules suite pins the exact wording so it cannot quietly return.

📝
Finding 2 — a request could be born approved (security)

The create rule accepted any document, including one that arrived fully approved with whatever day count its author liked. Created requests must now start life pending — whoever creates them — checked by prefix so renaming the approval stages cannot lock employees out. The two guards are deliberately separate functions (reading the old document is an error during a create), and a tripwire test guards that separation.

🚪
Finding 3 — the success screen was a dead end (usability)

The browser run submitted a request, then looked for the way back to the list. There was none: the screen offered "Request more leave" only, and clicking My Leave in the menu changed nothing because the route never changed. An exit button now returns to the list. A small thing — and exactly the kind a person hits in the first thirty seconds of using the app.

Worth recording too: the live harness itself produced two instructive failures on the way — passing the raw login where the app-shaped user belongs (every approver silently role-less), and signing out inside the very session being tested (a perfectly working rule denied an unauthenticated write). Both are documented in the harness, because the next person to test this module will make one of those mistakes again.

06 What testing cannot tell you

An honest list, because an evidence document that claims everything proves nothing.

🎨 Whether it impresses a human

The browser steps prove the screens work; they cannot prove the screens feel good. That judgement belongs to the first real user — which is the point of the demo.

📱 A physical phone in a hand

Testing used a desktop-class browser window. The layouts are responsive by construction, but a thumb on a factory floor is the only true test of a thumb on a factory floor.

📋 Whether the assumptions suit HR

The day-counting is proven correct against the settings that exist. Whether those settings are the right ones for this company — 21 days, Sundays, the leave year — is HR's question, and every one of them is a setting, not a rebuild.

📈 Scale beyond today's data

Every query shape the app issues was verified against the live database with the indexes that serve it. Two hundred simultaneous staff is a forecast, not a measurement.

07 Cleaning up the test data

Layers 3 and 4 did their job against the real database, which means the test data is real too.

Seventeen leave requests, each tagged LIVE-TEST in its handover note, were created across the runs: the approved chain, the rejection, the cancellations, the HR-lodged request, and the browser submissions. Deleting documents is owner-only by design — a test suite that could delete production data would be a test suite worth worrying about — so the list is handed over instead: run npm run test:live and the final test prints every document ID with its status.

⚠️
Two of them are currently approved

Until they are deleted, those two count towards the test employee's used days, exactly as real approved leave would. Deleting the full LIVE-TEST list restores her balance to what it should be. Until then, treat the test account's "Already taken" figure as inflated by the tests, not by holidays she never took.

08 The verdict

What all of this adds up to.

Every rule the Leave module claims to enforce — the arithmetic, the chain, the refusals, the privacy, the offline exception — is now either proven against the production database or pinned by an automated test that fails the moment someone breaks it. The two security holes that were found were of a kind no mock or unit test could ever see: they only existed in the gap between what the app promised and what the database enforced. They are closed, and the tests that found them now stand permanent guard.

What remains open is exactly what should remain open: the questions only HR can answer, waiting as settings; the demo, waiting for its audience; and the live test accounts, waiting to be retired.

✅
The one-line summary for management

The leave system does what it says, refuses what it should refuse, keeps private data private, and can prove all three. Test it by all means — but the tests are already here, and they run.
